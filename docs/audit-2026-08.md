# Library Audit — August 2026

**Scope:** re-verify the June 2026 audit (`docs/audit-2026-06.md`) against current `main` (v1.14.0), then a fresh pass for bugs, missing official API surface, packaging, and consumer gaps. Triggered by a request to double-check the flagship package before more work.
**Method:** code is the source of truth. June claims were checked against `src/`. New findings were checked against `src/`, the published npm `1.14.0` metadata, tsd-mono call sites, and the **now-public** official spec:
- https://raw.githubusercontent.com/soundcloud/api/master/openapi/api.yaml
- https://developers.soundcloud.com/docs/api/explorer/api.json
Anything not verifiable from code or that spec is marked **ASSUMED**.
**Baseline:** `soundcloud-api-ts@1.14.0`, clean `main` (`bd33b0c`).
**Follow-up:** P1 (H1–H3) and P2 (H4, H6, M1, M15, M17) were implemented in **1.14.1**. This document is the pre-fix finding list; see `CHANGELOG.md` 1.14.1 for what landed.

---

## Executive summary

The June 2026 fixes **still hold**. `dedupe` / `cache` / `cacheTtlMs` / `fetch` are wired. `toBase64` is used. Per-grant OAuth wire formats are unchanged and still match production. Class ↔ standalone path parity is intact. The June remaining list is still accurate.

This pass found **new High issues the June audit did not catch**, plus a real official-API gap now that SoundCloud publishes the spec:

1. **The published package export map does not match `dist/`.** `require("soundcloud-api-ts")` resolves to a file that is not in the tarball. ESM consumers work only because `exports.import` accidentally points at the CJS build.
2. **`SoundCloudError.errorCode` does not read the OAuth `error` field.** The auth guide tells consumers to branch on `err.errorCode` for `invalid_grant`. OAuth token errors put the code in `body.error`. tsd-mono already works around this.
3. **`onTokenRefresh` has no in-flight guard.** Concurrent 401s each call refresh. SoundCloud rotates refresh tokens, so this can invalidate a live session.
4. **Pagination snapshots the access token and bypasses auto-refresh / client retry config.**
5. **The official OpenAPI spec is public.** Coverage tooling still uses dead URLs and claims the spec is inaccessible. Several current endpoints (`/me/feed`, recently-played, upload, user/me repost lists, related artists, storefront) have no wrapper.

No Critical production-outage class was found in the request path itself. The two June trust-breakers (silent no-op config, OAuth doc drift) have not recurred.

## New findings

### High

**H1 — Published `exports` / `main` do not match `dist/`.**

tsup emits CJS as `dist/index.js` and ESM as `dist/index.mjs` (`package.json` has no `"type": "module"`). The published `1.14.0` metadata is:

```
main:     ./dist/index.cjs          ← file does not exist
module:   ./dist/index.js           ← this file is CJS
exports.import:  ./dist/index.js    ← CJS, not ESM
exports.require: ./dist/index.cjs   ← file does not exist
```

Same mismatch on `./types` (`types/index.cjs` does not exist). `bin` points at `./dist/cli.js`, which does exist (CJS) — CLI require path is fine.

Effect: `require("soundcloud-api-ts")` fails with `ERR_MODULE_NOT_FOUND`. ESM `import` works only because Node/bundlers can load the CJS file named `.js`. Native ESM consumers never get `index.mjs`.

Verified: local `dist/` listing + `npm view soundcloud-api-ts@1.14.0 exports`.

**Fix:** point `require` / `main` at `dist/index.js`, `import` / `module` at `dist/index.mjs` (and the same for `./types`). Add a publish-time assertion that every `exports` target exists. Patch release.

**H2 — `errorCode` ignores the OAuth `error` field the auth guide tells people to use.**

`SoundCloudError` sets `errorCode` from `body.error_code` only (`errors.ts:97`). OAuth `/oauth/token` errors use the RFC field `error` (e.g. `"invalid_grant"`). The constructor *message* falls through `body.error`, but `errorCode` stays `undefined`.

`docs/auth-guide.md:253-269` shows a raw body `{ "error": "insufficient_scope" }` and then a table of `errorCode` values including `invalid_grant`. The recommended check `err.errorCode` does not see those codes.

tsd-mono `TRefreshUserTokens.ts:50-57` already documents this and checks `body.error` first:

> SoundCloudError … puts the OAuth error code in `.body.error` … `.errorCode` → parsed from `body.error_code` (if present)

This is the June consumer gap, now confirmed in production code.

**Fix (non-breaking):** `errorCode = body.error_code ?? body.error ?? undefined`. Add `isInvalidGrant` / `isAuthError` getters keyed to the codes tsd-mono already uses (`invalid_grant`, `invalid_token`, `invalid_request`, `unauthorized_client`, `access_denied`). Pin with a token-endpoint 400/401 body fixture. Do **not** treat bare HTTP 401 as permanent — that was a tsd-mono reconnect-loop incident.

**H3 — Concurrent `onTokenRefresh` has no shared promise.**

`scFetchCore` (`http.ts:329-342`) calls `onTokenRefresh()` independently on every 401. There is no module-level / client-level in-flight guard. SoundCloud rotates refresh tokens on each successful refresh (**ASSUMED**, documented in tsd-mono). N concurrent 401s ⇒ N refresh calls ⇒ N−1 `invalid_grant` and a dead session.

tsd-mono’s shared client (`packages/helpers/src/SCClient.ts`) does **not** currently set `onTokenRefresh` — it refreshes out of band — so this is latent for that consumer. Anyone following `docs/auth-guide.md` §3 *does* hit it.

**Fix:** coalesce refresh on the client (same pattern as `soundcloud-api-ts-next` `ensureClientToken`). Document “persist the new refresh token atomically.”

**H4 — Pagination snapshots the token and skips auto-refresh + client retry config.**

```ts
// SoundCloudClient.ts:225-228, 245-247, 265-267
const token = this._accessToken;
return paginate(firstPage, (url) =>
  scFetchUrl(url, token, undefined, onReq, this.config.fetch));
```

- Token is captured at `paginate()` start. A refresh mid-walk is ignored.
- `scFetchUrl` has no `onTokenRefresh`. A 401 on page 2 throws instead of refreshing.
- Third arg is `undefined`, so `maxRetries` / `retryBaseDelay` / `onRetry` / `onDebug` fall back to `DEFAULT_RETRY` even if the client configured `maxRetries: 0`.
- A `{ token }` override on the first-page call is ignored for `next_href` (uses the stored token, or **no Authorization** if none is stored).

**Fix:** pass a getter (or re-read `this._accessToken` per page), thread `refreshCtx` into `scFetchUrl` (or route continuations through `scFetch`), and pass the client’s `RetryConfig`.

**H5 — Official spec is public; coverage tooling is dead.**

`tools/openapi-sync.ts:18-21` fetches:

- `https://raw.githubusercontent.com/soundcloud/api/master/docs/public.yaml` (wrong path)
- `https://developers.soundcloud.com/api/explorer/sound-cloud-api.json` (wrong path)

The live spec is `openapi/api.yaml` / `docs/api/explorer/api.json`. The spec has **no `operationId`s**. `coverage-check.ts` only counts `operationId`, so a successful fetch would still write `total: 0`. `coverage-baseline.json` still says the spec is not public. CI `openapi-coverage` is `continue-on-error` theater.

`IMPLEMENTED_OPERATIONS` is a hand-maintained alias list that does not match spec path/method (e.g. `post_me_followings_user_id` vs actual **PUT**, `get_tracks_track_id_likes` vs `/favoriters`, `delete_oauth2_token` vs `POST /sign-out`).

**Fix:** point sync at the two live URLs; key coverage off `METHOD path` instead of `operationId`; regenerate the baseline against the real spec.

**H6 — Persistent cache keys contain the access token.**

```ts
const key = `GET ${options.path} ${options.token ?? ""}`;
```

README tells people to plug in Redis/KV. The access token becomes a Redis key (logs, eviction dumps, shared clusters). Keying is otherwise correct (GET-only, path includes query, token separates users). Hash or omit the token from the stored key (keep it in process-local dedupe).

### Medium

**M1 — Network failures are not retried.** `isRetryable` is HTTP 429/5xx only (`http.ts:113-115`). A thrown `fetch` (`TypeError: fetch failed`, DNS, reset) exits immediately. Same on `scFetchUrl`. Transient transport errors are common on Azure Functions / Vercel.

**M2 — `/me/activities*` is deprecated; `/me/feed` is not wrapped.** Official spec marks `/me/activities`, `/me/activities/all/own`, `/me/activities/tracks` deprecated and adds:

| Method | Path | Notes |
|---|---|---|
| GET | `/me/feed` | Current activity feed |
| GET | `/me/feed/tracks` | Track feed |
| GET | `/me/recently-played/tracks` | Last 25; no pagination |
| GET | `/me/reposts/tracks` | |
| GET | `/me/reposts/playlists` | |
| GET | `/users/{urn}/reposts/tracks` | |
| GET | `/users/{urn}/reposts/playlists` | |
| GET | `/users/{urn}/related` | Related artists |
| POST | `/tracks` | Upload (`multipart` + `track[asset_data]`) |
| PUT | `/tracks/{urn}/storefront` | Artist storefront |
| GET | `/tracks/{urn}/preview` | 302 preview |

Highest-value for tsd-mono-class consumers: **recently-played**, **feed**, **user/me repost lists**, **related users**. Upload/storefront are creator-app features.

**M3 — `getTracks` uses deprecated `ids=`.** Spec: `ids` is deprecated; prefer `urns` (`soundcloud:tracks:1,...`). Client still sends `/tracks?ids=` (`SoundCloudClient.ts:907`, `getTracks.ts`). **ASSUMED** `ids` still works; it may disappear.

**M4 — Search is a thin `q` + hardcoded `limit=10` + deprecated `offset`.** Spec search supports `urns`, `genres`, `tags`, `bpm`, `duration`, `created_at`, `access`, `show_tracks`, `limit` up to 200, and `linked_partitioning`. The client always uses `limit=10` and `offset=10*pageNumber` (`searchTracks.ts:24`). Offset is deprecated in the spec.

**M5 — `getRelated` is typed as `SoundCloudTrack[]`; spec `200` is paginated `Tracks`.** Both class and standalone omit `linked_partitioning`. Tests mock a bare array. Live shape is **ASSUMED**. If SC returns `{ collection, next_href }`, every `.forEach` / `.title` caller is wrong at runtime.

**M6 — `TokenProvider` / `TokenStore` are documentation-only.** Exported from `src/index.ts` but never read by `SoundCloudClient`. JSDoc on `refreshIfNeeded` says “Called automatically when a request returns 401” (`token-provider.ts:37-41`). That is false unless the consumer wires `onTokenRefresh` themselves. Same drift class as June’s phantom config.

**M7 — `SoundCloudToken.refresh_token` is required.** Client-credentials responses typically have no refresh token. Type is a lie for the most common grant.

**M8 — Cache is not invalidated on writes.** A cached `GET /tracks/:id` stays stale after `like` / `update` / `delete`. Interface has `delete()`; nothing calls it. Document, or invalidate on mutating methods.

**M9 — `next_href` / `future_href` typed as required `string`.** Last page omits or nulls them. JSDoc already says “or null/empty”. Type should be `string | null | undefined`.

**M10 — `UpdateTrackParams` missing official write fields** (`permalink`, `embeddable_by`, `release_date`, `streamable`, `commentable`, `reveal_stats`, `reveal_comments`, `metadata_artist`) and still has unofficial `release_day`/`month`/`year` / `bpm` / `key_signature`.

**M11 — `offset` / `limit` of `0` are dropped.** `limit ?` / `offset ?` treat `0` as absent (`SoundCloudClient.ts:1115` and standalone twins).

**M12 — Standalone `signOut` ignores injected `fetch`.** Class uses `this.config.fetch`; standalone always uses global `fetch` (`signOut.ts:18`). Only twin mismatch on the whole surface.

**M13 — No `secret_token` on private track/playlist GETs.** Spec supports `secret_token` on `GET /tracks/{urn}` and `GET /playlists/{urn}`.

**M14 — `/me/connections` is not in the current public spec.** Implemented and typed; may need elevated access or may be gone. Mark **ASSUMED**.

**M15 — `setToken` does not clear a refresh token when omitted.** `if (refreshToken !== undefined) this._refreshToken = refreshToken` (`SoundCloudClient.ts:193`). After `setToken(clientCredentialsAccess)` a previous *user* refresh token remains; later `onTokenRefresh` can refresh the user session while calls use a client token. Auto-refresh calling `setToken(access, newToken.refresh_token)` when the grant omits `refresh_token` keeps the old refresh token (good for rotation-omit; bad if SC returned a deliberate empty). Auth-guide `InMemoryTokenStore` assigns `this._refresh = refresh` and *does* clear when omitted — the two contracts disagree.

**M16 — `RawClient` follows redirects; `scFetch` does not.** `scFetch` uses `redirect: "manual"` so `/resolve` returns `Location`. `RawClient` uses fetch default `"follow"` (`raw.ts:88-92`), so `sc.raw.get('/resolve?url=...')` can return the target JSON (200) instead of a 302. Raw also has no retry, no 401 refresh, and JSON-only bodies (cannot POST `URLSearchParams` for OAuth).

**M17 — Success-path `response.json()` is uncaught.** A 200 with a non-JSON body throws raw `SyntaxError`, not `SoundCloudError` (`http.ts:270-271`, `416`). `RawClient` swallows parse errors.

### Low

**L1 — CLI secrets file is world-readable.** `saveConfig` is `writeFileSync` with no `mode: 0o600` (`cli.ts:52-54`). `~/.sc-cli.json` holds `clientSecret` + tokens.

**L2 — CLI OAuth `state` is the literal `"cli-login"`.** No CSRF check on the callback (`cli.ts:212-244`). Callback server has no timeout.

**L3 — `Retry-After` HTTP-date is ignored.** `Number("Wed, 21 Oct 2015 …")` is `NaN`, so the client falls back to exponential backoff (`http.ts:122-127`). Seconds form works and is capped at 60s.

**L4 — Cache hits emit no `onRequest` telemetry.** A cached GET is invisible to `onRequest`. tsd-mono’s `[SC]` logs would under-count.

**L5 — AGENTS.md “How to Add a New Endpoint” is wrong.** Tests are not in `src/<category>/__tests__/`; they live in `src/__tests__/` + `standalone/`. Checklist omits `registry.ts` (gotcha 15 mentions it).

**L6 — `SoundCloudConnection` is missing from `soundcloud-api-ts/types`.** Exported from the main entry, not `src/types/index.ts`.

**L7 — `getSoundCloudWidgetUrl()` still does not compose with `soundcloud-widget-react`.** Returns a pre-encoded fragment; the widget package encodes again. Documented on the widget side; this package’s helper JSDoc still does not warn.

**L8 — Track comments send unofficial `threaded=1&filter_replies=0`.** Not in the public spec. **ASSUMED** still accepted.

**L9 — `getAuthorizationUrl` never sends `scope`.** Spec marks `scope` required (example `"default"`). **ASSUMED** SC still accepts omit.

**L10 — No first-class abort/timeout** (June remaining #1). Still the right next minor if consumers ask.

**L11 — `sc-cli auth` wipes a previous login session.** It writes a new config object with only `clientId` / `clientSecret` / client-credentials `token` (`cli.ts:188-189`), dropping `refreshToken`. `cmdMe` then treats the leftover or replacement access token as “logged in.”

**L12 — `Retry-After: ""` is treated as 0.** `Number("") === 0` → immediate retry (`http.ts:125-126`). HTTP-date still falls through to backoff (L3).

**L13 — `AutoRefreshContext.getToken` is never read by `scFetch`.** Dead field (`http.ts:80`). Namespaces pass `options.token` from their own getter.

## Verified correct (no action)

- Per-grant OAuth wire formats, class ↔ standalone path/method/body parity (except `signOut` fetch injection).
- Retry: 429 + 5xx only, `Retry-After` seconds honored and capped 60s, 4xx (non-429) throw immediately, 401 goes to refresh not retry, token-endpoint 401 does not recurse.
- PKCE S256 via Web Crypto, base64url, no padding.
- Deduper key includes method + path + token; cache same; mutations not cached; `sc.raw` not cached/deduped.
- `redirect: "manual"` so `/resolve` 302 returns `Location`.
- Like/repost boolean-swallow is documented on both sides.
- `getTracks` 200-ID client guard still in both twins.
- Follow is **PUT** `/me/followings/{id}` — matches the spec (registry name is wrong, implementation is right).
- Runtime has no Node-only APIs except the CLI (`fs` / `http` / `os`). `toBase64` still has a `btoa` fallback.
- tsd-mono `RefreshSCUserToken` correctly calls `client.auth.refreshUserToken` (body credentials). Do not bypass with direct `fetch`.
