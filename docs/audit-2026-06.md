# Library Audit — June 2026

**Scope:** full doc/code consistency sweep + code audit of `soundcloud-api-ts`, triggered by the llms.txt OAuth doc-drift incident that nearly broke tsd-mono (stale v1.13.2 note claiming all OAuth grants use body credentials; corrected in `82cae43`).
**Method:** every behavioral claim in README.md, AGENTS.md, llms.txt, llms-full.txt, CHANGELOG.md, and JSDoc was verified against `src/`. Code was treated as the source of truth throughout. Anything not verifiable from code alone (live SoundCloud endpoint behavior) is marked **ASSUMED**.
**Result:** audited at v1.13.4, fixed and bumped to v1.14.0. All fixes are non-breaking. Suite: 332 passed / 5 skipped (integration, env-gated); 100% line and function coverage; build (tsup), lint, and typecheck green on Node 24.

---

## Executive summary

The incident class that bit tsd-mono — docs describing behavior the code does not have — was **systemic, not isolated**. The worst instance: since v1.12.0 the package has documented in-flight GET deduplication, a pluggable cache, and fetch injection as flagship features (README comparison table, AGENTS.md, both llms files, CHANGELOG), while the `dedupe`, `cache`, and `cacheTtlMs` config options were **never read by any code**, and `fetch` only reached `sc.raw`. A documented `AbortController` config option never existed in the type at all. Separately, the 1.13.3 OAuth fix silently regressed the cross-runtime base64 guarantee that 1.13.1 had introduced, by reverting to raw `Buffer.from`.

The per-grant OAuth wire formats (the production-critical paths) were verified correct and left untouched: `client_credentials` sends `Authorization: Basic` with only `grant_type` in the body; `refresh_token` and `authorization_code` send `client_id`/`client_secret` in the form body. Class methods and standalone twins are in exact parity on every endpoint path.

Fix strategy: where docs promised config options that consumers may already be passing (and that typecheck), the code was wired up to match the docs (non-breaking, fulfills the published contract). Where docs described things that never existed (`AbortController`) or overstated coverage (telemetry "every code path"), the docs were corrected to match the code.

## Findings

### Critical

**C1 — `dedupe`, `cache`, `cacheTtlMs` config options silently ignored (v1.12.0–v1.13.4).**
Evidence: declared in `src/client/SoundCloudClient.ts:47-52`; a repo-wide grep for `config.dedupe|config.cache|config.cacheTtlMs` returned zero uses. `InFlightDeduper` (`src/client/dedupe.ts`) and `SoundCloudCache` (`src/client/cache.ts`) existed and were unit-tested but never instantiated by the client. Documented as working in README ("In-Flight Deduplication & Caching" section, comparison table), AGENTS.md gotchas 8–9, llms.txt, llms-full.txt:306-308, and CHANGELOG v1.12.0 ("default: true"). A consumer passing a Redis cache or `dedupe: false` got a silent no-op.
**Fixed** (`9e2caf5`): wired into `scFetch` for client-namespace GETs. Dedupe key = method + path + token; cache consulted before fetch, populated on success with `cacheTtlMs` (default 60000 per docs). `sc.raw.*` and pagination `next_href` fetches are not deduped/cached — docs now say so explicitly.

**C2 — `fetch` injection only reached `sc.raw`.**
Evidence: `src/client/SoundCloudClient.ts:174` was the only use of `config.fetch`; `scFetch`/`scFetchUrl` (`src/client/http.ts`) called global `fetch` unconditionally. README "Runtime Portability", the comparison table row "Fetch injection (Workers/Bun/Deno) ✅", AGENTS.md gotcha 7, and llms claims all said otherwise.
**Fixed** (`9e2caf5`): `config.fetch` now reaches all namespace methods (via the refresh context), `sc.auth.*`, `auth.signOut`, and pagination `next_href` fetches (new optional `fetchImpl` param on `scFetchUrl`).

### High

**H1 — Cross-runtime base64 regression in both `getClientToken` implementations.**
Evidence: `src/client/SoundCloudClient.ts:328` and `src/auth/getClientToken.ts:29` used `Buffer.from(...)` directly — a crash on Cloudflare Workers/browsers (no `Buffer`), contradicting README "No Node-only APIs are used at runtime" and the v1.13.1 changelog, which introduced `toBase64` (`src/utils/base64.ts`) for exactly this. The 1.13.3 Basic Auth fix reintroduced raw `Buffer.from`; v1.13.2's changelog even records deleting the `toBase64` imports.
**Fixed** (`395a0d0`): both use `toBase64` again. Wire format byte-identical in Node; tests pinning the Basic header pass unchanged. The `btoa` fallback path is now also unit-tested (`83469ce`).

**H2 — Documented `AbortController` config option never existed.**
Evidence: absent from `SoundCloudClientConfig` (`src/client/SoundCloudClient.ts:25-55`); no abort/signal/timeout code anywhere in `src/`. Yet README:494, AGENTS.md gotcha 7, llms.txt:232, llms-full.txt:304, and CHANGELOG v1.12.0 all documented it; the README/llms example would not even typecheck.
**Fixed** (`6f7b1fb`): removed from all docs, with a note to bake cancellation into an injected `fetch`. Implementing real abort support is feature work for a future minor — see "Remaining".

**H3 — Stale version headers in llms.txt / llms-full.txt (`v1.13.2`).**
Evidence: line 1 of both files vs `package.json` 1.13.4. This is precisely the drift vector from the original incident — an agent reading the file header would anchor on 1.13.2-era behavior.
**Fixed** (`6f7b1fb`): headers now track the release (v1.14.0); the per-grant OAuth notes themselves (corrected earlier in `82cae43`) were verified accurate against `src/auth/*` and left as-is.

### Medium

**M1 — Class `getUserToken`/`refreshUserToken` sent `redirect_uri=undefined` on the wire.**
Evidence: `this.config.redirectUri!` (`src/client/SoundCloudClient.ts:360,394`) serialized through `URLSearchParams` as the literal string `"undefined"` when `redirectUri` was not configured — an opaque server-side failure instead of a clear client error (`getAuthorizationUrl` already threw properly).
**Fixed** (`fc184d7`): both throw `"redirectUri is required for …"` before any network call. (Whether SoundCloud actually requires `redirect_uri` for the `refresh_token` grant is **ASSUMED** from the existing signatures; the parameter is still sent as before.)

**M2 — `sc.auth.*` ignored the configured retry options.**
Evidence: `Auth.fetch` passed `refreshCtx = undefined` to `scFetch` (`src/client/SoundCloudClient.ts:275` pre-fix), so token-endpoint calls always used `DEFAULT_RETRY` regardless of `maxRetries`/`retryBaseDelay`/`onRetry`/`onDebug`.
**Fixed** (`9e2caf5`): Auth now builds a context from config (without `onTokenRefresh` — a 401 from the token endpoint must throw, not recurse). Test pins `maxRetries: 0` ⇒ exactly one attempt.

**M3 — README Quick Start contradicted its own auth table.**
Evidence: README:134 called `sc.me.getMe()` right after `getClientToken()`, while the "Auth at a glance" table (and AGENTS.md, llms.txt, docs/auth-guide.md) correctly state `/me` requires a user token. **ASSUMED** (live behavior) but three docs + the guide agree, and the consuming repo's 401 experience supports it.
**Fixed** (`6f7b1fb`): Quick Start no longer calls `/me` with a client token.

**M4 — Telemetry "fires on every code path" overclaim.**
Evidence: `RawClient` (`src/client/raw.ts`) never emits `onRequest`; `auth.signOut` uses a bare fetch with no telemetry. The claim in README:554 / AGENTS.md gotcha 5 was scoped to client-namespace requests.
**Fixed** (`6f7b1fb`): docs now state the exclusions. Adding raw-client telemetry is listed under "Remaining".

**M5 — Node version inconsistency.**
Evidence: README badge said "Node ≥22"; README Requirements, AGENTS.md, and `engines` say `>=20`; CI tests 22 and 24 only.
**Fixed** (`6f7b1fb`): badge now matches `engines` (≥20). Note: the dev toolchain (vite 7 / vitest 4) needs Node ≥20.19 to run tests, and CI does not exercise Node 20 — see "Remaining".

**M6 — CHANGELOG v1.12.0 describes features the tagged code did not have** (dedupe/cache wiring, fetch+AbortController injection) — the same failure class as the 1.13.2 entry.
**Fixed** (`6f7b1fb`): correction blockquote added under the 1.12.0 entry (history preserved, Keep-a-Changelog style); the 1.14.0 entry records the actual wiring. The 1.13.2/1.13.3/1.13.4 entries were re-verified against the current code and are accurate. Per-tag verification of older entries (e.g. 1.11.3's claim that the standalone was "already correct") was not performed — marked **ASSUMED** historical record; it is internally consistent with the 1.13.2→1.13.4 sequence.

### Low

**L1 — CLI: browser never opened on Windows.** `start "<url>"` in cmd.exe treats the quoted URL as a window title (`src/cli.ts:222-228` pre-fix). **Fixed** (`65bcba9`): `start "" "<url>"`.
**L2 — Duplicate `likeTrack`/`unlikeTrack` implementations.** Byte-identical copies in `src/likes/index.ts` and `src/tracks/likeTrack.ts`/`unlikeTrack.ts` (only the tracks copies were package-exported). **Fixed** (`65bcba9`): likes module re-exports the single implementations.
**L3 — README markdown bug.** The `sc.raw` lines after the Client Class listing sat outside the code fence (README:282-285 pre-fix). **Fixed** (`6f7b1fb`).
**L4 — AGENTS.md gotcha numbering** restarted at 6 after 15. **Fixed** (`6f7b1fb`): 16/17/18.
**L5 — `getTracks` 200-ID limit undocumented in llms files and README method listing.** The guard exists (`src/tracks/getTracks.ts:31`, class `SoundCloudClient.ts:878`) and the JSDoc documents it, but the quick references didn't. **Fixed** (`6f7b1fb`). The actual server-side cap is **ASSUMED** (~200, per the 1.13.1 note "likely caps at ~200"); the client guard is a hard 200.
**L6 — README CLI feature bullet said `sc-cli tracks <id>`**; the command is `track`. **Fixed** (`6f7b1fb`).
**L7 — Untested public surface.** Standalone `getTracks` (including the 200-limit guard) and standalone `getMeConnections` had **zero** test coverage; the `toBase64` btoa fallback and the `_meta` response metadata were unexercised. **Fixed** (`83469ce`); plus a pin that `authorization_code` sends body credentials and no Basic header (`fc184d7`). No tautological tests were found worth deleting; one dead test helper (`makeClient` in raw.test.ts) was removed (`65bcba9`).
**L8 — pnpm 10 blocked esbuild's install script** on every `pnpm install` (`ERR_PNPM_IGNORED_BUILDS`). **Fixed** (`1c89bc3`): `pnpm.onlyBuiltDependencies: ["esbuild"]`.

### Verified correct (no action)

- **Per-grant OAuth wire formats** (production-verified, untouched): class + standalone `getClientToken` send Basic Auth with `grant_type=client_credentials` only (`src/client/SoundCloudClient.ts:323-337`, `src/auth/getClientToken.ts`); class + standalone `refreshUserToken` and `getUserToken` send `client_id`/`client_secret` in the body with no Basic header (`SoundCloudClient.ts:386-398,355-369`, `src/auth/refreshUserToken.ts`, `src/auth/getUserToken.ts`). Pinned by `src/__tests__/auth.test.ts` and `standalone/auth.standalone.test.ts`.
- **Class ↔ standalone parity**: every endpoint pair builds an identical path/query string (verified by exhaustive grep diff); like/repost boolean-swallow semantics match and are documented on both sides.
- **Retry behavior matches docs**: 429 + 5xx retried, `Retry-After` honored capped at 60s (`http.ts:110-115`), exponential backoff `base × 2^attempt` + 10% jitter (`http.ts:118-119`), non-429 4xx throw immediately, 401 handled by refresh not retry.
- **Pagination matches docs**: `next_href` followed (`paginate.ts:34`), `fetchAll.maxItems` honored; `/oauth` paths routed to `secure.soundcloud.com`, everything else to `api.soundcloud.com` (`http.ts:179-180`).
- **PKCE**: S256 via WebCrypto, base64url without padding (`src/auth/pkce.ts`) — matches docs; RFC 7636 compliant.
- **Errors**: `SoundCloudError` carries `status`/`statusText`/`errorCode`/`errors[]`/`body` + convenience getters exactly as documented (`src/errors.ts`); status propagates for consumer branching on 401/403/429; no swallowed errors outside the documented boolean like/repost helpers.
- **CLI secrets**: credentials/tokens are stored in `~/.sc-cli.json` (standard CLI config; documented) and never logged or echoed; `--json` output contains only API response data.
- **signOut endpoint** (`https://secure.soundcloud.com/sign-out`, JSON body): **ASSUMED** — not verifiable from code; pinned by tests as-is.

## Remaining (not fixed, with reasons)

1. **Abort/timeout support** — `AbortController` was doc-only vapor; real cancellation support is new API surface (likely a `signal`/`timeoutMs` option) and belongs in a planned minor, not an audit pass.
2. **Telemetry for `sc.raw.*` and `signOut`** — would make the original "every code path" claim true instead of scoped. Small, but changes `RawClient`'s constructor plumbing; deferred to keep this pass minimal. Docs now state the exclusion.
3. **Dedupe/cache for pagination `next_href` fetches** — `scFetchUrl` has no dedupe/cache. Defensible behavior (continuation pages are rarely concurrent-identical), now documented; unify later if consumers ask.
4. **CI does not test Node 20** although `engines` claims `>=20`, and the vitest 4 / vite 7 dev toolchain itself needs ≥20.19. Options for the maintainer: add a Node 20 job (runtime-only smoke test of `dist/`), or bump `engines` to `>=22` in the next **major** (changing `engines` is breaking-adjacent — out of scope here).
5. **`scFetch`/`scFetchUrl` duplication** — ~120 lines of near-identical retry/parse/telemetry logic; a refactor to share a core would reduce future drift risk (the audit had to verify both copies). Pure refactor, no behavior change — left for a quiet cycle.
6. **Boolean like/repost error swallowing** — `likeTrack` etc. return `false` for *any* failure (401 vs 404 vs 429 indistinguishable). Documented behavior on both class and standalone sides, so changing it is breaking; consider `{ ok, error }` returns or thrown errors in v2.
7. **CHANGELOG pre-1.13 entries** — verified for internal consistency only, not against each git tag (low value vs cost). Bottom link references also stop at 1.9.0; cosmetic.

## Consumer-driven gaps (for tsd-mono-class consumers; listed, not implemented)

- **`isInvalidGrant` / auth-error classification helper.** tsd-mono keeps duplicate direct-fetch token-refresh code partly because the library offers no way to distinguish a *permanent* refresh failure (`invalid_grant` → re-auth required) from a *transient* 401. `SoundCloudError` already exposes `errorCode` and `body`, but SoundCloud's actual refresh-failure body shape (`error` vs `error_code` field, exact values) is **ASSUMED** territory — it must be captured from production before a helper can be keyed to it correctly. Recommended next step: tsd-mono logs `err.body` on refresh failures for a week, then the library adds e.g. `get isInvalidGrant()` against the observed shape (non-breaking).
- **Refresh-token rotation guidance.** SC rotates refresh tokens on every refresh (each response carries a new one). The library handles storage via `setToken`, but a documented "persist the new refresh token *atomically* or you lose the session" pattern in docs/auth-guide.md would address the distrust that led to the duplicate code.
- **Telemetry on raw + abort support** (above) — both repeatedly useful for consumers wrapping the library in their own observability.
- With this pass, the two concrete trust-breakers found in the library itself (silent no-op config, doc drift) are fixed and regression-pinned; nothing else in `src/` blocks tsd-mono from relying on the library's token refresh exclusively once the error-classification gap is closed.
